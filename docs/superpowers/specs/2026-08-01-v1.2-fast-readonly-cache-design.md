# TikHub 小红书 MCP v1.2：快速只读查询与分页缓存设计

## 目标

在不降低 API Key 安全性、不放开任意 URL、也不改变 79 个白名单接口范围的前提下，改善三类体验：

1. 保留 v1.1 已修复的 `TIKHUB_API_KEY` 传递方式；
2. 减少插件启动和本地请求的额外耗时；
3. 对重复的只读查询不再重复访问 TikHub，且数据查询不需要逐次人工确认。

本版本号为 `1.2.0`，同时发布 GitHub 插件和 Windows ZIP 安装包。

## 范围与非目标

### 本次包含

- 对 9 个 MCP 工具声明正确的只读属性；
- 使用“仅写入操作需要确认”的 Codex 配置建议；
- 插件改用锁定、可复用的 Python 运行环境；
- 在 MCP 进程内增加成功响应的 5 分钟分页缓存；
- 增加显式刷新能力；
- 更新测试、说明文档和 ZIP 分发包。

### 本次不包含

- 不新增写入、发布、评论、点赞或账号操作；
- 不缓存 API Key，也不把 Key 写入日志、工具结果或缓存键；
- 不承诺缩短 TikHub 服务端本身、网络链路或付费接口的处理时间；
- 不在同事电脑上静默修改 Codex 的全局配置。

## 方案比较

| 方案 | 优点 | 不足 | 结论 |
| --- | --- | --- | --- |
| 仅缓存“请求 50 条”的完整结果 | 改动最少 | 请求 300 条时无法复用前 50 条 | 不采用 |
| 分页内存缓存 | 前 50 条可复用，缓存自动随服务结束清除，无本地数据残留 | 仅对同一 MCP 进程和 5 分钟内有效 | **采用** |
| 持久化磁盘缓存 | 跨重启也可加速 | 易产生陈旧数据和本地隐私数据 | 不采用 |

## 缓存设计

### 缓存范围

缓存记录的单位是“一次允许调用的接口页”，而不是一次自然语言需求。缓存键由以下内容构成：

- 白名单接口名；
- 规范化后的业务参数（字典键排序、空值处理一致）；
- 页码或游标等分页参数；
- 其他会影响返回结果的排序与筛选参数。

认证字段永远不参与缓存键，Key 也不会保存到缓存值或日志。

### 50 条到 300 条的复用规则

以同一关键词、相同排序与筛选条件为例：

1. 用户先取得前 50 条；MCP 缓存实际访问过的第 1、2、3…页；
2. 5 分钟内用户再要求 300 条；已经缓存的页直接返回，不会再次访问 TikHub；
3. MCP 只请求尚未缓存的后续页；
4. 若之后只要前 50 条，也仍直接复用已有缓存。

因此，已缓存的前 50 条不会产生新的 TikHub 接口访问。实际节省的调用次数取决于接口单页返回条数和已缓存的页数。

### 有效期与刷新

- 默认 TTL：300 秒（5 分钟）；
- 只缓存成功响应；401、402、403、404、超时、参数错误和本地异常均不缓存；
- 缓存只存在于当前 MCP 服务内存，服务或 Codex 会话重启后自动清空；
- `xhs_search_notes`、笔记/评论/用户/热榜工具及 `xhs_call` 增加 `refresh: bool = false`；
- 用户明确说“重新获取”“刷新”或“不要缓存”时，调用方传入 `refresh=true`，强制实时请求，并用成功的新结果更新缓存。

## 免逐次确认与安全边界

所有 9 个工具都保持只读。服务端会为工具补充 MCP 只读标注：

- `readOnlyHint=True`；
- `destructiveHint=False`；
- 对实际访问 TikHub 的查询如实保留其外部网络性质；
- `xhs_status` 与 `xhs_list_endpoints` 不发起 TikHub 请求。

文档和 ZIP 配置示例将使用 `default_tools_approval_mode = "writes"`。这意味着已标注为只读的查询可直接执行，未来若新增写入型工具仍会要求确认。

Codex 的个人配置属于用户控制范围：ZIP 安装脚本不会静默改写它。文档将提供一次性、仅针对本 MCP 的配置步骤；使用该步骤后，数据查询不再逐次弹出确认。

查询仍可能产生 TikHub 费用。工具描述会保留该提示，但不会为每一次相同的只读查询要求额外许可。

## 启动与请求性能

### GitHub 插件

当前 `uv run --with mcp==2.0.0` 会在运行时创建临时依赖上下文。v1.2 改为插件目录内声明依赖并提交锁文件，启动命令使用锁定依赖的持久项目环境。首次安装仍可能下载 Python 或依赖；完成后续启动会复用该环境。

### Windows ZIP

ZIP 保留安装脚本创建的固定虚拟环境。它不使用临时 `uv --with` 依赖层，并会将说明更新为只读免确认配置。

### 传输层

服务层会确保一个 MCP 进程内的客户端可复用，避免每次工具调用重复初始化本地客户端。实现必须保留现有错误映射和 API Key 脱敏行为；若底层 SDK 不支持安全复用，则以分页缓存和固定运行环境作为确定性加速手段，不为“复用连接”而改变 TikHub 请求语义。

## 实现边界

- `xhs_mcp_server.py`：工具标注、`refresh` 入参和描述；
- `xhs_mcp_service.py`：TTL 分页缓存、规范化缓存键、刷新逻辑、并发去重与客户端生命周期；
- 插件的 `.mcp.json`、`pyproject.toml`、`uv.lock`：固定运行环境；
- README、安装/配置/错误说明：配置方法、缓存与刷新语义；
- 分发构建脚本与 ZIP 内容：同步 v1.2 文件和版本号。

`xhs_call` 仍只接收登记的 `resource.method` 名称；`refresh` 是本地控制参数，不会转发给 TikHub。任何用户传入的 URL、认证字段或保留参数仍会被拒绝。

## 验收与测试

1. 原有 79 个接口均仍可列出，且任意 URL 仍被拒绝；
2. 两次相同页请求中，第二次不调用假客户端并返回第一次数值；
3. 请求前 50 条后再请求至 300 条时，已缓存页不调用假客户端，只调用缺失页；
4. `refresh=true` 必定绕过缓存并刷新该页；
5. 402、403、网络异常均不进入缓存，且错误中不泄露 API Key；
6. 9 个工具均带只读标注；
7. 锁定环境首次安装、后续启动和 MCP STDIO 握手均通过；
8. ZIP 在干净 Windows 虚拟环境安装后，`xhs_status` 可用；余额充足时，用真实 Key 做一次搜索冒烟测试。

## 风险与处理

- **数据时效性**：默认最多使用 5 分钟前的同页结果；用户可显式刷新。
- **费用**：未缓存的新页仍会产生 TikHub 请求与可能的费用。
- **Codex 策略差异**：不同用户的全局许可策略可能覆盖插件建议；文档提供精确的、只针对该 MCP 的 `writes` 配置。
- **首次启动**：首次下载运行环境无法与已安装环境一样快；后续启动通过持久环境改善。
